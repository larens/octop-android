# Octop Android Today 主动 Agent 改造方案

> 调研与方案日期：2026-10-27
> 范围：移动端 Today 页、主动采集与聚合、消息推送、建议到执行的闭环
> 本文中的 Today.ai 产品描述仅基于公开官网、官方文章和用户提供的界面截图；其内部排序算法、模型提示词和服务端实现没有公开，不将推断写成事实。

## 0. 开篇结论

**只做一件事：**把当前“最近会话列表”式 Today 页改造成一个围绕用户目标持续运转的主动工作台：Agent 发现变化、合并证据、判断与目标的差距、准备下一步，并在风险边界内提醒或等待确认。

**解决的问题：**用户不再自己轮询聊天、任务、记忆和外部网站，也不需要阅读一堆原始资讯；每天只处理少量“为什么现在值得看、证据是什么、下一步能做什么”的卡片。

**项目优先级：P0。**它决定 Octop 是“需要用户不断发起问题的聊天工具”，还是“离线时也能替用户关注、收集、整理和推进事项的个人 Agent”。

### 一句话产品定义

> Today 不是新闻流，也不是任务列表；它是 Agent 根据用户明确目标与兴趣，对内外部变化做差异计算后生成的、可追溯且可行动的每日工作面。

### 核心产品公式

```text
主动帮助 = 稳定身份与权限
        + 可观察的数据源事件
        + 可编辑的长期记忆/目标
        + “目标 - 现状”的差距判断
        + 与失败代价匹配的行动权限
        + 克制的聚合与推送
```

## 1. Today.ai 是怎样“主动”的

### 1.1 公开资料中可以确认的产品行为

Today.ai 的公开页面与官方文章共同呈现了以下机制：

1. **结构化且可检查的长期记忆。**记忆不是不可见的聊天历史，而是人物、项目、偏好、承诺等可读、可改、可删的事实；官方说明建议为事实保存来源、状态、时间、作用域、保留期限和行动影响。
2. **连接已授权的数据源。**公开示例包括日历、邮件、笔记、文件和健康数据；连接器是可选、可撤销且按能力范围授权的。
3. **由时间和变化触发。**产品在晨间与晚间两个固定锚点主动出现；日程移动、临近截止、等待审批、睡眠变化等有后果的变化可以触发额外建议。
4. **先筛选，再聚合。**晨间简报不是复述所有日程和未读消息，而是挑选会影响当天决策的少量事项；没有变化的背景默认折叠，缺失或过期的数据源必须明示。
5. **从事实走向动作。**卡片不仅给摘要，还准备草稿、寻找时间段、整理资料或提出日程调整；涉及发信、改日历、对外发送等动作时，公开说明强调先取得用户确认。
6. **离线持续执行。**官网将云端任务执行、连接器和云端电脑作为持续运行能力，意味着采集与处理不依赖移动端常驻。
7. **通过反馈逐步收敛。**官方文章提出保留真正改变决定或帮助准备的内容，删除反复被略过的内容；晨报应当是“仍能保护关键决策的最小集合”。

Today.ai 的公开隐私政策还说明：连接第三方数据源前会告知读取/写入范围；AI 处理可能使用第三方模型服务；健康等敏感信息需要额外同意。这个边界对 Octop 的自托管方案尤其重要：**数据存储在自己的服务端，不等于搜索查询、模型上下文和连接器数据不会离开服务端。**

### 1.2 公开资料没有说明的部分

以下内容没有公开证据，不能直接照搬或声称已知：

- 兴趣画像的具体 embedding、知识图谱或排序模型；
- 每张卡片的打分权重、阈值和去重算法；
- 网页采集使用的搜索供应商、抓取频率与全文存储方式；
- 移动推送使用的厂商、通知 payload 和送达保障；
- Agent 内部 prompt、评估器和多 Agent 编排方式。

因此，本方案复制的是**可观察的产品原则和闭环**，不是猜测 Today.ai 的内部技术实现。

### 1.3 信息是如何聚合呈现的

综合官网、官方文章和用户提供的 6 张截图，Today 的聚合单位不是“来源”，而是“对用户有意义的一件事”。同一件事可以合并会话、网页、日程、任务状态和记忆证据，再形成以下叙事结构：

```text
发生了什么
  -> 为什么现在重要
  -> 与哪个目标/兴趣相关
  -> 哪些证据支持，哪些来源没有覆盖
  -> 当前判断与不确定性
  -> Agent 已经准备了什么
  -> 用户现在可以采取哪个动作
```

截图体现了 6 种值得保留的聚合模板：

| 模板 | 聚合方式 | 适合场景 |
|---|---|---|
| 晨间简报 / 晚间收尾 | 跨来源压缩成当天主线 | 每日决策、遗漏回收 |
| 时间线 | 早/中/晚或多次事件串成一个结论 | 故障、研究线索、项目变化 |
| 长短窗口 | “今天”与“未来 119 天”并列 | 展览、旅行、长期机会 |
| 主题簇 | 多条信号归并为同一问题 | 研究选题、内容提纲 |
| 取舍卡 | 把两个候选与机会成本并列 | 排期、优先级、资源冲突 |
| 外部样本对照 | 证据强度、可用状态和限制并列 | 产品选型、竞品、技术调研 |

截图是目标体验示意，不是已发生的真实事件；其中的产品名、日期和结论不能作为项目数据或产品事实使用。

## 2. 参考文章给出的设计约束

微信文章《Personal Agent 落地思考：主动性从哪来，又卡在哪？》给出了比“定时搜一下网页”更完整的判断框架。

### 2.1 主动性的三个基础条件

- **身份与权限：**Agent 有稳定身份，才能在用户离线时被日程、Git、邮件等事件唤醒并使用授权工具。
- **数据源：**时间规则和外部变化提供“什么时候该动”。只有身份没有数据源，Agent 无事可做。
- **记忆：**目标、偏好和历史反馈决定“什么值得告诉这个用户”。只有数据源没有记忆，推送会像群发资讯。

### 2.2 主动的本质是“目标 - 现状”

只有“用户喜欢 AI”还不足以产生高质量主动帮助。系统至少需要知道：

- 目标：例如“完成 Today 页改造”“形成每周 AI 产品判断”“稳定维护开发工具链”；
- 成功或验收规则：例如“有一手来源”“与已有结论冲突时必须标注”“本周必须形成可评审产物”；
- 现状：当前任务、会话结论、外部变化、尚未确认的事项；
- 差距：缺什么证据、什么条件阻塞、什么时间窗口正在关闭；
- 下一步：继续收集、整理草稿、提醒、请求确认或执行低风险动作。

这意味着兴趣管理不能只有关键词，还要允许用户描述目标、当前优先级、验收规则和有效期。

### 2.3 两根独立的权限轴

每张 Today 卡都要明确两件事：

1. **问题是谁定义的：**用户明确提出、用户配置规则、Agent 从目标计算、还是 Agent 猜测用户可能关心；
2. **Agent 可以做到哪一步：**记录、告知、建议、准备可审阅产物、确认后执行、自动执行。

推荐的默认政策：

| 问题来源 | 默认行动上限 | 示例 |
|---|---|---|
| 用户明确任务/规则 | 低风险、可撤销、可验证时可自动执行 | 定时整理公开网页，写入草稿箱 |
| Agent 从明确目标计算差距 | 默认做到“准备产物”，写操作等待确认 | 发现缺少竞品证据，先补齐调研稿 |
| Agent 推测潜在兴趣/目标 | 只告知或建议，不自动改变外部状态 | “这可能与你最近的 3D 生成研究有关” |
| 涉及他人、公开发送、付费、删除、权限 | 无论来源均逐次确认 | 发邮件、改日历、删除文件、购买 |

### 2.4 长周期必须防止目标漂移

长期目标会变化。系统应记录 `last_confirmed_at` 和 `review_at`；当目标长期未确认、来源冲突、连续低反馈或行动影响变大时，把任务降级为“等待校准”，而不是继续按旧理解努力。

## 3. 当前 Octop Android 的能力与缺口

### 3.1 已经具备，可直接复用

| 能力 | 当前实现 | 在新方案中的用途 |
|---|---|---|
| 会话状态 | `ThreadEntity.turnActive / awaitingUser / unreadCount` | 生成“正在处理”“等你确认”卡 |
| 对话与工具轨迹 | `ChatSocket`、`tool_result`、`turn.ended`、trajectory | 展示执行过程、证据和结果 |
| 服务端自动任务 | cron 支持 `cron / interval / date / agently` | 定时采集、事件触发、晨报/晚报 |
| 自然语言任务 | `NaturalLanguageTaskRepository` 调用结构化 cron 工具 | 用一句话新建或修改关注任务 |
| 连接器 | 任务可绑定 MCP server | 邮件、日历、搜索等来源访问 |
| 本地结构化记忆 | 人物/项目/偏好/承诺，有来源会话字段 | 个性化过滤和来源追溯 |
| 服务端记忆聚合 | 画像、当前关注、情绪日记、记忆沉淀 | 目标背景与近期状态 |
| 长任务通知 | `TurnService` + 低优先级进行中通知 | 显示用户发起任务仍在执行 |
| Deep link | `octopmobile://thread/{thread_id}` | 从通知回到执行会话 |

自然语言任务链路已经建立了一个重要安全惯例：**不能根据 Agent 的自然语言回复猜测成功，必须收到期望的结构化工具结果并核对准确任务 ID。**Today 卡片发布、确认和执行也应沿用这一原则。

### 3.2 当前 Today 页为何还不够主动

当前 `TodayPane` 只读取会话和本地记忆，并按 `awaitingUser / turnActive / 最近会话` 分组。它存在以下缺口：

1. “最近推进”只是最近会话，不代表对目标重要；
2. 没有读取自动任务、任务执行结果、连接器或网页信号；
3. 没有“变化前后”数据，无法可靠地说“发生了什么变化”；
4. 没有目标与验收规则，无法计算差距；
5. 没有证据引用、来源覆盖和不确定性；
6. 没有统一的建议动作与审批状态；
7. 现有通知只表示聊天回合在后台运行，不负责服务端主动消息送达；
8. 协议已记录 `/api/notifications/ws` 可用于 cron/主动关怀，但移动端尚未实现；仅依赖 WebSocket 也无法保证 Android 进程被杀后的送达。

## 4. 目标用户体验

### 4.1 Today 首页信息架构

Today 首页继续位于当前四栏底部导航，不新增一级入口。页面采用“摘要在前、证据渐进展开、输入持续可用”的结构：

1. **页头：**`Today`、未读数量、筛选/主动设置按钮；
2. **状态条：**最近更新时间、已覆盖/失效的数据源、手动刷新；
3. **今日主线：**最多 1 张，告诉用户当天最值得关注或推进的核心取舍；
4. **等你确认：**最高优先级，显示将执行的动作、影响范围和确认按钮；
5. **现在可以推进：**Agent 已准备好草稿、清单、对照表或下一步；
6. **值得了解：**与兴趣/目标高度相关的外部变化，默认只显示摘要；
7. **已处理/稍后：**折叠，避免完成事项继续占据注意力；
8. **底部会话式输入：**“管理你的兴趣、目标和优先级……”，用于新增关注、纠正判断、调整频率，不把用户送去复杂设置表单。

首页不再单独展示“最近记忆”。记忆是卡片为什么出现的依据，应在卡片的“为什么推荐给我”中可追溯；完整管理仍留在记忆栏。

### 4.2 统一卡片结构

所有卡片使用同一最小结构，具体模板只改变中部可视化：

```text
[类型 · 目标/主题] [新/更新/待确认]
一句结论
为什么现在值得看

变化 / 时间线 / 对照 / 取舍 / 进度（按模板选一种）

依据：3 个来源 · 1 个来源不可用 · 更新于 08:00
为什么推荐给我：关联“主动 Agent 改造”目标

[主动作] [稍后] [不感兴趣/调整关注]
```

每张卡必须包含：

- `why_now`：现在出现的触发原因；
- `goal_or_interest`：关联目标或兴趣，区分“用户明确”与“Agent 推测”；
- `summary`：结论，不复述所有原文；
- `evidence_refs`：来源标题、URL/会话/任务、时间和摘录；
- `coverage`：哪些来源已检查，哪些不可用或过期；
- `confidence`：高/中/低及理由，不能只给一个神秘分数；
- `proposed_action`：下一步及预期产物；
- `action_policy`：自动、需确认或仅建议；
- `lifecycle`：新建、已读、稍后、已确认、执行中、已完成、失败、已过期。

### 4.3 卡片详情页

点击卡片打开详情，而不是立刻跳进原始会话。详情页包含：

1. 完整结论和影响；
2. 事实、推断、建议三段分离；
3. 证据列表与原文跳转；
4. 目标与记忆引用，可纠正或解除关联；
5. Agent 的处理记录：何时搜索、调用什么连接器、哪些步骤失败；
6. 建议动作预览、影响范围、可撤销性和确认入口；
7. “继续聊这件事”，进入对应线程并保留卡片上下文。

### 4.4 主动设置

设置应回答四个问题，而不是暴露模型参数：

- **关注什么：**目标、兴趣、项目、排除主题；
- **从哪里看：**会话、记忆、任务、指定网站/搜索、已授权连接器；
- **什么时候打扰：**晨报、晚报、即时阈值、安静时段、每日上限；
- **能做到哪一步：**只收集、可整理草稿、确认后执行、明确白名单内自动执行。

新增关注仍采用当前自然语言方向。例如：“每天工作日 8 点帮我关注 Android Agent 和个人知识库的新进展，只要一手来源；和 Octop 有直接关系时给出落地建议，不要自动发消息或改代码。”Agent 必须在缺少频率、来源范围或动作边界时追问，不能静默补全。

## 5. Agent 主动收集与处理闭环

### 5.1 端到端流程

```text
用户目标/兴趣/验收规则
    +
时间触发 / 外部事件 / 任务状态 / 手动刷新
    ↓
采集：会话、记忆、任务、连接器、Web 搜索
    ↓
规范化：统一时间、来源、主题、实体、证据片段
    ↓
去重聚类：相同事件合并；旧卡只做更新，不重复发新卡
    ↓
差距计算：目标 - 当前状态 -> 问题/机会/阻塞
    ↓
价值与风险门控：相关性、时效、影响、置信度、失败代价
    ↓
生成结构化 TodayCard（不是解析一段 LLM prose）
    ↓
聚合成晨报/晚报或即时高价值提醒
    ↓
用户反馈 / 确认 -> 执行 -> 校验真实结果 -> 更新卡片与记忆
```

### 5.2 信号候选的最小打分

首版不用训练推荐模型，采用可解释规则即可：

```text
value = 目标相关性
      + 时间紧迫度
      + 对当前决策的影响
      + 是否解除阻塞
      + 来源可信度
      - 重复度
      - 不确定性
      - 打扰成本
```

硬门槛优先于总分：

- 没有来源或把推断伪装成事实：不发布；
- 只因“关键词相同”但无法解释与目标关系：进入候选箱，不推送；
- 来源不可用：允许发布“覆盖不足”卡，但不得声称“没有变化”；
- 与旧卡相同且没有实质变化：合并更新，不通知；
- 外部写操作：没有匹配审批政策就只能准备草稿。

### 5.3 Web 搜索策略

“关注某个领域”不等于每天把同一个宽泛关键词交给搜索引擎。推荐流程：

1. 从明确目标生成 3-8 个可审阅的查询主题，并让用户可编辑；
2. 优先订阅官方博客、GitHub Release、论文、RSS 等一手或稳定来源；
3. 搜索用于发现未知来源，固定来源用于持续跟踪；
4. 为每个来源保存 `last_seen_fingerprint / published_at / fetched_at`；
5. 只把“新增或发生实质更新”的内容送入分析；
6. 同一事实至少保存原始 URL、标题、发布时间和支持该结论的摘录；
7. 搜索查询只携带完成任务所需的最少兴趣信息，不把完整记忆或私人会话发送给搜索服务商。

### 5.4 从建议到执行

建议动作分为 5 档：

| 档位 | 能力 | 默认策略 |
|---|---|---|
| A0 | 记录/聚合 | 自动 |
| A1 | 通知/提醒 | 遵守频率与安静时段后自动 |
| A2 | 生成草稿、清单、候选方案 | 自动，但清楚标注未执行 |
| A3 | 可撤销的私域写入 | 逐次确认；未来可由用户配置白名单 |
| A4 | 对外发送、删除、付费、权限、安全或高影响动作 | 每次确认并记录审计，不继承历史授权 |

执行完成必须由工具返回结构化结果，随后再读取实际状态验证。例如“日历已移动”要以日历连接器回读结果为准，不能以 Agent 说“已经完成”为准。

## 6. 数据与接口方案

### 6.1 服务端作为 Today 真值来源

主动任务在服务端离线运行，Today 卡也应由服务端持久化。移动端 Room 只做离线镜像，沿用现有 cron 的“服务端先成功，本地后更新”原则。

MVP 最少新增 4 个服务端概念：

| 概念 | 关键字段 | 说明 |
|---|---|---|
| `goal` | id, title, definition, success_rules, source, status, review_at | 用户目标与验收规则 |
| `interest_monitor` | id, query_scope, sources, schedule, action_ceiling, goal_id | 主动采集配置；底层可映射 cron |
| `today_card` | id, kind, title, summary, why_now, confidence, lifecycle, goal_id, thread_id, timestamps | 首页聚合项 |
| `evidence_ref` | card_id, source_type, source_id/url, title, excerpt, observed_at, freshness | 可追溯证据与覆盖状态 |

审批不必首版另造一套复杂工作流，可复用会话 `hitl_required`，但 Today 卡需保存 `approval_thread_id / tool_call_id / action_state`，才能从卡片准确回到待确认动作。

### 6.2 建议 API

```text
GET  /api/agents/{agent_id}/today?cursor=&state=&kind=
GET  /api/agents/{agent_id}/today/{card_id}
POST /api/agents/{agent_id}/today/{card_id}/feedback
POST /api/agents/{agent_id}/today/{card_id}/snooze
POST /api/agents/{agent_id}/today/{card_id}/archive
POST /api/agents/{agent_id}/today/{card_id}/open-action-thread

GET  /api/agents/{agent_id}/goals
POST /api/agents/{agent_id}/goals
PATCH /api/agents/{agent_id}/goals/{goal_id}

GET  /api/agents/{agent_id}/interest-monitors
POST /api/agents/{agent_id}/interest-monitors
PATCH /api/agents/{agent_id}/interest-monitors/{monitor_id}
```

发布卡片使用受限的结构化工具 `today_card_publish`，字段由服务端校验：至少有证据、`why_now`、目标/兴趣关联、建议动作和权限档位。不要让移动端解析 cron 会话里任意格式的文本来猜卡片。

### 6.3 推送通道

推送应拆成“生成、入箱、投递、阅读”四个独立状态，避免把“生成成功”误认为“用户已收到”。

推荐组合：

- **持久化通知箱：**服务端先保存卡片和未读状态，保证任何通道丢失后都能补拉；
- **前台实时：**实现已有 `/api/notifications/ws`，接收 `today.card.created/updated` 后刷新；
- **Android 后台：**生产版接 OS push。为减少隐私暴露，push payload 默认只放 `agent_id + card_id + priority`，正文由 App 鉴权后拉取；
- **自托管无 Google 模式：**首版允许“打开 App 后补拉 + 可选周期同步”，后续再评估 UnifiedPush/ntfy 等自托管通道；周期同步只负责追赶通知，不负责执行 Agent 任务；
- **Deep link：**新增 `octopmobile://today/{card_id}`，直接打开卡片详情，不先落到会话列表。

## 7. 通知与注意力策略

### 7.1 三种投递级别

| 级别 | 进入 Today | 系统通知 | 示例 |
|---|---|---|---|
| 摘要 | 是 | 仅晨报/晚报入口 | 常规行业更新、无截止机会 |
| 重要变化 | 是 | 合并通知 | 截止提前、任务解除阻塞、来源结论冲突 |
| 等待确认 | 置顶 | 是，可带时限 | 草稿待发送、日历变更待确认 |

默认不为每张卡分别发通知。建议试点上限：即时通知每天不超过 3 次，其他内容合并到晨报/晚报；安静时段仅保留用户明确标记的紧急规则。

### 7.2 推送文案

通知只回答“为什么值得点开”，不在锁屏泄露敏感正文：

- 好：“一个变更影响了你今天的发布计划，已整理 2 个处理选项”；
- 差：“发现 17 条关于 AI 的新消息”；
- 好：“有一项外部动作已准备好，等待你确认”；
- 差：“Agent 已替你处理完成”（在实际回读验证前尤其不能这样写）。

## 8. 移动端改造清单

### 8.1 页面与状态层

| 改动 | 目标文件/模块 | 说明 |
|---|---|---|
| 拆出 Today 状态层 | 新增 `TodayViewModel` | 不再复用 `ThreadsViewModel` 拼页面 |
| Today 数据仓库 | 新增 `TodayRepository` | 服务端同步、Room 镜像、反馈和状态变更 |
| 卡片 DTO/Entity | remote dto + Room entity/dao | 结构化渲染，不解析 Markdown 猜动作 |
| Today 首页 | 重构 `TodayPages.kt` | 主线、待确认、可推进、值得了解、已处理 |
| 卡片详情 | 新增详情 Composable/route | 证据、覆盖、不确定性、执行记录 |
| 主动设置 | 新增设置页 | 目标、来源、频率、权限上限 |
| 会话式输入 | Today 页底部 composer | 复用自然语言任务交互与 IME 连续性原则 |
| 通知接入 | notification WS + push adapter | 卡片入箱、未读、Deep link |
| 导航 | `WorkbenchScreen` / Routes | 保持四栏结构，Today 子页隐藏底栏时避免闪动 |

### 8.2 与现有模块的边界

- **任务页**管理“何时运行、运行什么”；Today 展示“这次运行发现了什么、是否值得处理”。
- **记忆页**管理 Agent 长期相信什么；Today 只引用记忆解释推荐原因，不复制记忆管理能力。
- **会话页**处理深入讨论和 HITL；Today 提供入口与摘要，不重新实现聊天流。
- **Today 页**拥有跨域聚合、优先级、生命周期和反馈，是其他三栏的决策表面。

### 8.3 UI 视觉建议

沿用截图的“清晨蓝到暖白”背景、宽松圆角和大标题，但避免所有信息堆进一张超长卡：

- 首屏只露出主线、待确认和 1-2 张高价值卡；
- 时间线、证据对照、标签簇在详情中展开；
- 事实使用中性颜色，建议使用青色，风险/未验证使用琥珀色；
- 底部 composer 与导航保持固定，沿用项目已处理的 IME/底栏连续性约束；
- 卡片高度由内容决定，但列表摘要最多 3-5 行，详情页显示完整证据；
- 所有状态不仅依赖颜色，还要有文字/图标，支持无障碍与深色/大字体适配。

## 10. 成功指标与上线门槛

以下是 20-50 人试点的目标值，不是当前基线：

| 维度 | 指标 | 试点目标 |
|---|---|---|
| 相关性 | 被标记有用或产生打开/继续/执行的卡片占比 | >= 70% |
| 克制 | 每用户每日即时通知 P50 / P95 | <= 1 / <= 3 |
| 可追溯 | 重要事实带可打开证据的比例 | 100% |
| 诚实性 | 来源不可用时正确披露比例 | 100% |
| 执行安全 | 未确认的 A3/A4 外部写操作 | 0 |
| 闭环 | 已确认动作有结构化结果并回读验证 | 100% |
| 时效 | 事件触发到 Today 入箱 P95 | <= 5 分钟 |
| 晨报 | 配置用户在设定时间前生成成功率 | >= 99% |
| 信任 | 7 日内关闭全部主动通知的试点用户占比 | < 10% |
| 价值 | 每周至少一次因 Today 改变决定或省去检查的用户占比 | >= 50% |

上线硬门槛：零越权外部动作；零无来源的确定性重要结论；用户可以关闭某个监控、撤销连接器、删除卡片和纠正引用的记忆。

## 11. 风险与应对

| 风险 | 具体表现 | 应对 |
|---|---|---|
| 通知疲劳 | 每个新网页都推送 | 双锚点简报、变化阈值、每日上限、相同事件合并 |
| 目标猜错 | 把近期聊天误当长期目标 | 标注来源；推测目标仅告知；要求用户确认后升格 |
| 目标漂移 | 三周前目标仍持续触发 | `review_at`、低反馈降级、关键节点重新确认 |
| 搜索幻觉 | 摘要与来源不一致 | 保存证据摘录；事实/推断分离；高影响结论要求一手来源 |
| 数据源失效 | 连接器断开却声称没有变化 | 显示覆盖与最近成功时间；旧结果标过期 |
| 越权执行 | 记住偏好被误当成授权 | 记忆、检索、建议、执行权限四层分离；A3/A4 逐次确认 |
| 隐私外流 | 私人记忆进入搜索或外部模型 | 最小化查询；按作用域检索；记录模型/连接器/搜索 egress |
| 卡片重复 | cron 多次生成同一事件 | `event_fingerprint + goal_id` 幂等；更新旧卡而非新建 |
| 移动端漏消息 | WebSocket 断开或进程被杀 | 服务端持久 inbox + OS push + 启动补拉，不依赖单一通道 |
| 状态错位 | Agent 说完成但工具失败 | 只接受结构化工具结果，必要时回读目标系统 |

## 12. 推荐的 MVP 取舍

第一版应该做：

- 3 类来源：现有会话/任务/记忆、Web 搜索、一个真实连接器；
- 4 类卡：晨晚简报、值得了解、现在可推进、等你确认；
- 3 个动作：继续研究、整理为产物、进入会话确认；
- 完整证据、来源覆盖、去重、通知上限和反馈；
- 服务端持久化与移动端离线镜像。

第一版不应该做：

- 为所有信息训练个性化推荐模型；
- 自动推断并直接启用长期目标；
- 自动发送邮件、改日历或对外发布；
- 多 Agent 群聊式编排；
- 把所有聊天和网页全文复制进长期记忆；
- 为追求“看起来很主动”而在无变化时生成内容。

## 13. 决策建议

建议按 Phase 0 -> Phase 1 -> Phase 2 -> Phase 3 推进，在真实用户连续使用 7 天、达到相关性和克制指标后，再投入后台 push 与 A3 行动闭环。最关键的技术决策不是卡片样式，而是：

1. Today 卡是否有服务端结构化真值，而不是移动端解析 Agent 文案；
2. 每条结论是否有证据、覆盖范围和不确定性；
3. 用户目标、Agent 推测和执行授权是否严格分离；
4. 通知是否由“实质变化和决策窗口”触发，而不是由内容数量触发。

只要这四点成立，现有 Octop 的 cron、连接器、会话、记忆和 HITL 已经足以搭起一个可信的主动助手；如果缺少其中任何一点，界面即使与截图完全一致，也仍只是漂亮的摘要流。

## 14. 手机作为数据采集入口

### 14.1 架构原则：服务端优先，手机补充

手机不能直接读取其他 App 的私有数据库。Android 沙箱、第三方平台条款和数据合规共同决定了采集路径必须分级：

```text
官方云 API / Webhook / 企业连接器
    -> 服务端 Connector（首选，稳定、可增量、用户离线也运行）

Android 系统数据层 / 用户主动分享 / 本机传感器聚合
    -> MobileDataHub（手机边缘采集器）
    -> 本地过滤、去重、脱敏、加密暂存
    -> 服务端统一 Ingest API

没有官方 API、没有系统数据出口、用户也未主动提供
    -> 不采集，不通过 Root、无障碍脚本或逆向数据库绕过
```

因此飞书日程和飞书聊天以服务端用户身份 OAuth/API 为主；系统日历、Health Connect、分享面板和经明确授权的通知摘要由手机补充。相同来源在服务端和手机同时出现时，统一事件层负责关联，而不是各自生成一份 Today 卡。

### 14.2 各类数据源可行性

| 数据源 | 推荐接入方式 | 可获得内容 | 限制与结论 | 优先级 |
|---|---|---|---|---|
| 飞书日程 | 服务端飞书 Calendar API；手机系统日历作补充 | 日程、变更、参会人、忙闲 | 服务端 API 最稳定。飞书官方也支持通过 CalDAV 将飞书日历同步到小米系统日历；其他 Android 可借助系统支持或 DAVx5。同步进入 Android Calendar Provider 后，Octop 经日历权限可读 | P0 |
| 手机系统日历 | Android `CalendarContract` | 用户授权的本地/系统账户日历 | 需要 `READ_CALENDAR`；只读用户选中的日历。不要默认把私人日历标题、描述和参会人全部上传 | P0 |
| 小米运动健康 | 先让小米运动健康写入 Health Connect，再由 Octop 读取 | 取决于小米实际写入的数据类型，可能包含步数、心率、睡眠、锻炼 | 不直接读取小米 App 私有库。必须在目标手机、目标版本上检查 Health Connect 的“数据和访问权限”；未写入的数据 Octop 无法取得 | P0 试点 |

| 飞书聊天 | 服务端飞书 IM API/事件订阅，按用户可见范围读取 | 授权范围内的群聊、私聊、消息搜索与事件 | 需要企业应用权限和用户身份；按白名单群/联系人/时间窗采集，不默认全量入仓 | P1 |

| 企业微信 | 企业合规的会话内容存档能力 | 企业开启且获授权范围内的工作会话 | 是企业级服务端方案，需要管理员开通、员工/外部联系人告知同意及合规评审，不是手机通用读取能力 | 独立项目 |
| 其他办公聊天 | 官方 API/Webhook 优先；分享面板其次；通知摘要最后 | 平台授权消息或用户选择的片段 | 通知不是历史记录，只能作为“发生了变化”的低可信信号 | P1 |

| 照片、文件、录音 | 系统 Photo Picker、Storage Access Framework、分享面板 | 用户明确选择的内容 | 当前 App 已支持 `ACTION_SEND/SEND_MULTIPLE`，应从“直接开新会话”扩展为“询问、存入收集箱、关联目标”三种去向 | P0 |

### 14.3 飞书日程的两种链路

**链路 A：服务端直连，推荐作为真值来源。**

```text
飞书 OAuth（用户身份）
  -> Calendar API / 日程变更事件
  -> Octop 服务端 Connector
  -> canonical calendar_event
  -> Today 差距判断与建议
```

优点是用户不打开手机也能同步，拥有稳定的外部 event ID、变更时间和删除状态，并可在确认后调用同一连接器修改日程。

**链路 B：飞书 -> CalDAV -> 手机系统日历 -> Octop。**

飞书官方支持生成 CalDAV 配置；小米日历可导入 CalDAV，其他 Android 设备可能需要 DAVx5 或厂商自己的 CalDAV 支持。Octop 只读取已经进入 Android Calendar Provider 的日历：

1. 用户在飞书生成设备专用 CalDAV 凭据；
2. 用户在小米日历或可信 CalDAV 客户端配置同步；
3. Octop 请求 `READ_CALENDAR`，列出可见日历并让用户逐个勾选；
4. 首次只读滚动窗口，例如过去 7 天到未来 90 天；
5. 后续按事件更新时间和内容指纹增量上传；
6. 服务端把系统日历副本与飞书 API 事件关联，飞书 API 版本优先作为权威记录。

不要让 Octop 保存飞书 CalDAV 密码；账户配置应留在系统/CalDAV 客户端。不要默认申请 `WRITE_CALENDAR`，等“确认后写入手机日历”成为明确需求再单独申请。

### 14.4 健康数据链路

Android 官方 Health Connect 是手机健康数据的正确汇聚层。它将步数、睡眠、心率、锻炼等记录结构化，并在用户授权后供其他 App 读取；支持后台读取，但需要额外权限和设备支持。

```text
小米运动健康 / Keep / 其他运动 App
  -> 用户在各 App 中开启写入 Health Connect
  -> 用户在 Health Connect 中逐数据类型授权 Octop 读取
  -> Octop 初次导入 + Changes 增量同步
  -> 本地按来源和时间去重/聚合
  -> 上传最少必要指标或原始记录
  -> 服务端形成 health_observation
  -> Today 在生活方式范围内提出建议
```

首版建议只申请：

- `StepsRecord`：每日总步数；
- `SleepSessionRecord`：睡眠起止、阶段和时长；
- `ExerciseSessionRecord`：运动类型、起止和时长；
- `HeartRateRecord` / 静息心率：仅在明确用例和单独授权后开启。

健康数据同步必须遵循：

1. **先做能力探测。**展示 Health Connect 是否可用、哪些 App 实际写入了哪些类型、最近一次数据时间；没有数据时说“该来源未向 Health Connect 提供”，不能说“用户今天没有运动”。
2. **累积指标用聚合 API。**Android 官方明确建议步数等累积类型使用 `aggregate()`，避免多个来源重复统计。
3. **保存数据来源。**使用 `DataOrigin` 区分小米、Keep、手机传感器等；同一时段多来源按用户指定的首选来源或确定规则合并，不能简单相加。
4. **增量同步。**首次默认仅回溯 30 天；更久历史需要额外历史读取权限。之后使用变化令牌/更新时间增量读取，处理删除记录并上传 tombstone。
5. **后台最小化。**通过 WorkManager 在充电或非低电量、网络可用时批量同步；不要常驻前台服务轮询。后台健康读取权限未授予时，降级为打开 App 时同步。
6. **只做生活方式建议。**诸如“睡眠不足，是否把高强度训练移到晚上”可以作为待确认建议；不得作诊断、风险预测或替代医生。

### 14.5 聊天数据的现实边界

**飞书。**服务端已有连接器配置体系，应增加用户身份的飞书消息连接器：用户选择允许的群、私聊、时间窗和字段；优先订阅新消息事件，定时补拉用于防丢。原文只进入短期事件仓，长期记忆必须经过提炼、来源标注和用户可纠正机制。

**个人微信。**可支持但不能全自动全量读取：

- 用户在微信中选中消息、合并转发或分享文件到 Octop；
- 分享入口先进入“手机收集箱”，用户选择关联目标/项目以及是否仅本次使用；
- 对于微信导出的合法文件，可通过 Storage Access Framework 由用户显式选择后导入；
- 可选的通知监听只记录用户白名单 App 的通知摘要，并把它当成“需要进一步检查”的信号；
- 不将通知摘要当作完整聊天事实，不因没收到通知推断“无人回复”；
- 不实现 Root、Hook、Accessibility 自动翻页、截屏 OCR 或读取微信数据库等方案。

**企业微信/受监管办公数据。**如果公司启用了会话内容存档，应作为独立服务端连接器接入。接入前确认企业管理员授权、员工与外部联系人告知同意、数据处理目的、保留期限和删除机制；不能由个人手机 App 绕过组织控制导出到私人仓库。

### 14.6 MobileDataHub 组件设计

在 Android 端新增一个明确受用户控制的数据源层：

```text
MobileDataHub
├── CalendarSourceAdapter
├── HealthConnectSourceAdapter
├── ShareInboxSourceAdapter
├── NotificationSignalAdapter（实验、默认关闭）
├── LocalIngestStore（加密暂存 + outbox）
├── SourcePermissionManager
├── MobileSyncWorker
└── MobileIngestClient
```

每个 Adapter 只负责读取和规范化，不直接调用模型。同步过程：

1. Adapter 从系统 API 读取获得授权的范围；
2. 在手机上先裁剪字段、移除不必要附件和敏感正文；
3. 写入本地加密 outbox，生成稳定 `event_id / dedupe_key`；
4. WorkManager 批量上传，服务端按 `event_id` 幂等接收；
5. 服务端返回 accepted/rejected 和新 cursor；
6. 客户端仅在服务端确认后清理 outbox；
7. 用户撤销来源时停止新采集，并提供“只停止”与“停止并删除历史”两个不同动作。

当前项目的 `ACTION_SEND/SEND_MULTIPLE` 已能接收文本、图片和文件，但会立即创建新会话。改造时把 `PendingHandoff` 扩成显式意图：

| 去向 | 行为 |
|---|---|
| 问问 Agent | 保持现有行为，建立会话并发送 |
| 存入收集箱 | 写入 `ShareInboxSourceAdapter`，等待聚合/分类 |
| 关联目标 | 选择目标或项目后入箱，允许后续 Today 主动跟进 |
| 仅本次使用 | 处理完成后过期，不晋升长期记忆 |

### 14.7 统一入仓协议

无论数据来自服务端连接器还是手机，都先写入统一事件层，不能直接写长期记忆：

```json
{
  "event_id": "device-or-connector-stable-id",
  "source_type": "android_health_connect",
  "source_account": "user-visible-alias",
  "source_record_id": "opaque-source-id",
  "event_type": "health.sleep_session",
  "occurred_at": "2026-10-26T22:40:00+08:00",
  "observed_at": "2026-10-27T08:02:00+08:00",
  "subject": "self",
  "payload": {},
  "provenance": {
    "device_id": "pseudonymous-device-id",
    "data_origin": "source-package-or-connector",
    "consent_version": "..."
  },
  "privacy_class": "sensitive_health",
  "retention_policy": "aggregate_after_30d",
  "dedupe_key": "...",
  "deleted": false
}
```

建议数仓分三层，但保持简单：

| 层 | 内容 | 默认保留 |
|---|---|---|
| 原始事件层 | 最小必要原始记录、来源、删除标记 | 短期；健康/聊天可配置 7-30 天 |
| 规范事实层 | 去重后的日程、每日健康聚合、消息行动项 | 按目标生命周期 |
| Agent 特征层 | “昨晚睡眠低于近 14 日基线”“会议提前两小时”等可解释特征 | 可重建，随来源删除 |

长期记忆只能保存用户确认的稳定偏好、目标、承诺或经过规则验证的事实；“昨晚只睡 5 小时”和“一条微信通知”属于短期状态，不能自动变成永久画像。

### 14.8 跨来源去重与权威级别

项目决定：飞书日历已经同步到 Android 系统日历，本版不再单独做飞书日历与系统日历之间的跨来源归一化，避免重复接入同一份数据。系统日历仍按自己的稳定事件标识更新和去重。

最容易出错的是同一信息从多个入口重复出现，例如飞书 API、CalDAV 系统日历和飞书通知都报告同一场会。

权威优先级建议：

```text
官方服务端 API 原始对象
  > Android 系统 Provider 中带稳定账户/事件信息的对象
  > 用户主动分享或导入的完整内容
  > 通知摘要
  > OCR/模型推断（首版不做自动采集）
```

去重不应删除低权威来源，而应建立 alias：`canonical_event_id -> [source_ref...]`。匹配优先使用外部稳定 ID；没有稳定 ID 时再用归一化后的标题、开始/结束时间、组织者和参与人指纹。模型不能自行判断两件事“看起来差不多”就永久合并，低置信匹配要保留为候选。

### 14.9 权限、隐私与用户控制

手机数据的授权页必须在开启前说明：

- 读取哪些 App/日历/健康数据类型；
- 是只在手机处理，还是上传到哪台 Octop 服务端；
- 原始数据保存多久，何时只保留聚合；
- 哪些数据会进入模型上下文，模型是否为本地或第三方；
- 是否会用于主动通知，默认通知频率；
- 如何暂停、撤销、导出和删除。

技术要求：

- 健康、聊天和通知数据分开授权，不能用一个“全部允许”；
- 使用 Android Keystore 保护设备密钥；敏感 outbox 加密或上传确认后立即删除；
- 上传使用设备级短期令牌，可单独撤销丢失手机；
- 服务端保存设备、来源、同意版本和每次读取/上传的审计记录；
- 搜索引擎不得收到聊天全文、健康详情或完整个人画像；
- 向外部模型发送健康/聊天数据前显示 egress 边界并允许关闭；
- 其他人的聊天、参会和健康信息按更严格的作用域、保留和外发规则处理；
- 删除必须传播到原始、规范、特征、卡片和可重建记忆，而不只是隐藏移动端列表。

### 14.10 移动端具体改动

| 改动 | 当前位置 | 建议 |
|---|---|---|
| 数据源入口 | Today 右上角主动设置 | 新增“手机数据”区，显示日历、Health Connect、分享收集箱、通知实验源的状态和最近同步 |
| 权限 | `AndroidManifest.xml` / Activity Result | 按功能延迟申请日历、Health Connect；通知监听跳转系统专用设置，不在首启索要 |
| 后台同步 | 当前没有 WorkManager | 新增唯一周期任务和一次性手动同步；服务端仍负责 Agent 调度，手机 Worker 只上传数据 |
| 本地数据 | `OctopDatabase` v3 | 新增 `mobile_sources / mobile_events / mobile_sync_state / mobile_outbox`，必须提供 v3 -> v4 迁移和测试 |

### 14.11 手机数据 MVP

建议先做以下闭环，不要一开始追求“汇总所有 App”：

1. 飞书服务端日程 + Android 系统日历，只读并去重；
2. Health Connect 的睡眠、步数和锻炼，首次仅导入 30 天；
3. 微信/浏览器/其他 App 的“分享到 Octop -> 收集箱”；
4. 手机端展示采集预览，用户可以删掉尚未上传的事件；
5. 服务端形成两个真实建议：日程冲突/准备窗口、睡眠与当天负荷的生活方式调整；
6. 连续试点两周后再决定是否开启通知监听实验和飞书消息白名单。

MVP 验收补充：

- 同一飞书日程经服务端 API、系统日历和通知出现时只生成一个事实和一张卡；
- 小米/Keep 未写入 Health Connect 时明确显示“来源未提供数据”，不展示零值；
- 撤销健康权限后 Worker 不再读取，删除请求能清掉服务端派生卡片；
- 微信数据仅在用户主动分享后入仓，App 在未授权时无法读取历史聊天；
- 用户可查看任一 Today 建议使用了哪些手机来源和哪些字段。

### 14.12 Today 建议执行闭环（已落地）

Today 卡片会保存真实执行会话、回合和状态：`prepared / running / waiting_confirmation / completed / failed`。点击“交给 Agent”只表示准备执行；创建并绑定服务端会话后，状态由聊天的 `turn.started`、`hitl_required`、`turn.ended` 和 `error` 事件推进。卡片可以直接回到执行会话，失败时展示原因；写操作仍沿用既有 HITL 确认，不因 Today 入口绕过审批。

服务端卡片列表会用 active turn 和 HITL store 校正非终态，重启 App 后仍能恢复“正在处理/等待确认”；没有收到终态时不会把“当前没在运行”误判为完成。服务端同时校验卡片、用户、agent 和 thread 的归属，移动端只在真实 thread 创建成功后上传关联，不保存 `draft-*`。
